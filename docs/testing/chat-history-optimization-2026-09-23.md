# 长聊天性能优化与真机复测：2026-09-23

本次修复了上一轮定位出的两个瓶颈：无 WebChat 订阅者时的全量历史回读，以及 Flutter 在历史前插时重排整页。保持现有消息组件、样式和 ACP 生命周期。

同一 PJD110 实机、同样的 Profile 配置与合成消息生成规则，10,000 条历史的单条修改保存返回中位耗时从 **22,787.08 ms 降至 77.22 ms**；追加 50 条历史至更新画面 Raster 完成，从 **311.49 ms 降至 46.70 ms**。真实快速滑动触发分页时，最慢 UI 帧从 **282.84 ms 降至 15.16 ms**。

基线为 `afcdc1962`，详细方法见[优化前真机报告](chat-history-device-performance-2026-09-23.md)。优化版为该提交加本轮工作区改动，未提交。两轮按先后顺序测量，未随机化，不应用小幅差异推断普遍提升。

## 实现

### Kotlin：避免构造无人接收的历史快照

`ConversationDomainService.publishMessagesReplaced` 改用 `RealtimeHub.publishSnapshot`。没有 WebChat Flow 订阅者时，不执行昂贵的 `listConversationMessages`；Flutter 的原生会话变更通知仍然正常发出。新 WebChat 客户端继续通过已有查询 API 获取初始状态，事件流原本就没有 replay。

有订阅者时仍使用原有快照内容和发布路径，保持 `messages_replaced` 协议及顺序，没有增加第二套 ACP reducer、事件协议或重试机制。新增测试验证无订阅者不读历史、有订阅者按序接收快照和后续事件、断开后停止构造快照。

**限制：连接 WebChat 时仍需构造完整历史，那个场景的保存延迟尚未解决。** 本轮保存收益只适用于没有 WebChat 订阅者的手机使用场景。

### Flutter：历史在稳定原点之前延伸

消息列表使用 `CustomScrollView.center` 与前后两个惰性 `SliverList`。保留首次加载的最早行作为稳定原点，新加载的旧记录向原点之前延伸；可见的原有行不再因为前插 50 条而整体改变子节点索引。删除基于估算总高度差的翻页后 `jumpTo` 补偿。

气泡、Markdown、行间距、左右边距、底部遮挡补偿、自动跟随和现有滚动物理继续复用。行的局部 Key 与用于消息导航的 GlobalKey 保留各自职责。无新增业务状态或消息转换逻辑。

这种布局是 Flutter 官方提供的历史前插保位方式。[CustomScrollView.center 示例](https://api.flutter.dev/flutter/widgets/CustomScrollView-class.html)

## 测量结果

除帧最大值与 P95 外，下表为中位数；时间单位 ms。

| 项目 | 1,000 条优化前 | 1,000 条优化后 | 10,000 条优化前 | 10,000 条优化后 |
| --- | ---: | ---: | ---: | ---: |
| 单条修改保存接口返回 | 933.60 | **19.38** | 22,787.08 | **77.22** |
| 追加历史 50 条：数据完成 | 48.63 | 39.25 | 42.93 | 32.77 |
| 追加历史 50 条：Raster 完成 | 313.64 | **55.67** | 311.49 | **46.70** |
| 最新 50 条读取与模型解码 | 58.56 | 54.04 | 51.76 | 48.49 |
| 最新 50 条读取 P95 | 69.54 | 67.40 | 63.09 | 60.09 |
| 最深一页读取 | 58.42 | 56.84 | 82.96 | 73.13 |
| 进程内重读首屏至 Raster 完成 | 69.92 | 70.03 | 62.31 | 69.09 |
| Activity 冷启动 TotalTime | 1,484 | 1,453 | 1,427 | 1,495 |
| 冷启动后 3 秒进程 PSS / MiB | 356.8 | 313.9 | 338.0 | 316.7 |

首屏和冷启动没有可确认的改善。优化后千条组仍有一次首屏重读 331.05 ms 的异常高值，未剔除；不能把本轮结果解释为所有操作都已流畅。

保存各 5 次，固定 50 个显示对象、每次仅替换一个对象，包含 MethodChannel、原生持久化及写后通知。两组测试时前台均为万条会话，与原测试一致。万条组优化后原始样本为 84.856、79.701、64.061、77.223、67.795 ms。此指标不是纯 SQL 事务时间。

分页读取每组预热 3 次后测 25 次；受控追加每组 5 次；打开每组 5 次；冷启动每组 3 次。全部冷启动均恢复正确会话且只加载 50 条。优化后完整扫描 20 / 200 页，得到恰好 1,000 / 10,000 个唯一消息 ID，无重复，总计 1.11 / 13.34 秒。

普通拖动仍采用 8 次交替方向、每次 1.8 秒，截去每个手势窗口前后 200 ms。优化后千条 / 万条有效帧数为 1,456 / 1,465，UI P95 为 0.815 / 0.801 ms，Raster P95 为 6.375 / 6.425 ms。这里只记录 Flutter 工作时间，不冒充 SurfaceFlinger 最终呈现 FPS。

万条会话的真实快速滑动复用 24 次 ADB 手势：100 ms 滑动、间隔 600 ms；第 20 次检查均确认加载量从 50 增至 100。

| 快速滑动指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 采集窗口内有效帧数 | 2,445 | 2,421 |
| UI P95 | 1.105 ms | 1.392 ms |
| UI 最大值 | **282.842 ms** | **15.155 ms** |
| Raster 最大值 | 7.433 ms | 7.479 ms |
| 单帧总耗时最大值 | 287.090 ms | 20.819 ms |

在同一份新建合成数据上重新安装旧 Profile 包，再安装优化包，各复测一次相同的 24 次真实手势：旧版最慢 UI 帧为 165.384 ms，优化版为 16.209 ms；均加载到 100 条。该交叉复核也重现了差异，原始结果保存在 `fling-baseline-repeat.json` 和 `fling-optimized-repeat.json`。

另一次受控追加 3 页，最慢 UI 帧从 261.28 ms 降至 15.44 ms。分页峰值显著下降，但 15 ms 仍超过 120 Hz 的约 8.33 ms 帧预算，不能声称完全没有超时帧。

复测使用同一设备、分辨率、密度、120 Hz、Flutter 3.47.2 Profile ARM64 AOT；原生依赖仍是 debug variant，不是完整 Release。优化轮持续 USB 充电，电池温度约 36.1→36.0°C，开始 thermal status 为 1。前轮约 33.4→36.8°C，因此小幅变化可能受环境和热状态影响。

## UI 与回归验证

- Flutter 全套 1,247 项通过；原生 `RealtimeHubTest` 的 3 项通过；改动相关静态分析无问题。
- 新增两种阅读位置的前插测试：插入 50 条历史后，同一可见文字的垂直位置误差不超过 0.5 像素，行重建数少于 15。换回原实现时这两个回归测试失败。
- 再补充并通过导航检查：从原点后方跳到新历史，再回到最新消息，跨越两个 Sliver 的负、正偏移均能定位。
- 真机在同一份合成会话、同一阅读位置分别安装前后 Profile 包截图。1080×2376 截图中，顶部导航区域 `(0,130)-(1080,320)` 与正文区域 `(0,320)-(1080,1900)` 逐像素相同。状态栏时间和输入框等动画区域不作逐像素相等承诺；人工核对样式与布局一致。
