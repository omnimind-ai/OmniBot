01 / Definition

它不是“提示词工程”，
而是运行时工程。

当模型需要读写文件、调用 shell、请求审批、恢复会话，或在失败后安全重试时，单靠 system prompt 已经不够。Harness 把这些不确定性收进一个可编排、可观测、可约束的执行边界。

System prompt

MODEL-SIDE

告诉模型“你是谁、应该怎么回答”。它影响推理与表达，但不能可靠地执行权限、保存状态或保证一次工具调用真的发生。

RUNTIME-SIDE

02 / Arrival

它是什么时候
被“引进”来的？

2022 — 2023

Prompt-centric

模型像一个聪明的聊天框。工程重点是 prompt、RAG 与输出格式。

2023 — 2024

Agent loop

工具调用与 ReAct 让模型开始“行动”，但循环、失败与上下文拼接各自为政。

2024 — 2025

Harness

随着 coding agent 进入真实仓库，执行边界、审批、恢复与观察性变成一等公民。

NOW

Runtime boundary

harness 开始与 ACP、MCP、插件和多 agent 协作对齐，成为产品与模型之间的操作系统层。

这里没有一个公认的“发布日期”。更准确的说法是：2024–2025 年，随着可执行 Agent 产品化，harness 这个工程边界逐渐显形并被命名。

03 / Four shapes

四个名字，
四种重心。

Codex

REPO-NATIVE

把任务放进代码仓库的生命周期：读上下文、改文件、跑检查、汇报 diff。核心资产是可审计的工程工作流。

重心：代码上下文 × 受控执行

cc / Claude Code

TERMINAL-FIRST

以对话驱动终端工作。它把 shell、文件树与人类确认放在同一条短路径上，强调连续的现场感。

重心：人机共驾 × 即时反馈

pi agent

MINIMAL CORE

尽量薄的 agent 核心：把循环、工具和会话接口留在一个容易替换的边界里，适合实验与二次构建。

重心：可组合 × 可移植

dsh

SHELL-NATIVE

把 Agent 当作开发者 shell 的延伸：命令、脚本与环境变量就是原生语言，适合自动化与批处理。

重心：脚本化 × 低摩擦

本页把 cc、pi agent、dsh 作为“形状样本”来讨论：它们不一定共享同一套官方定义，但都在回答同一个问题——模型如何稳定地进入工作现场。

04 / The next layer

未来，harness 会
变厚还是变薄？

厚在运行时，
薄在编排。

安全、状态、权限、观测、恢复这些“脏活”会越来越厚；但业务团队不该反复手写 agent loop。好的 harness 把复杂性沉到底层，把上层留给目标、策略与组合。

判断：厚的是可靠性，不是流程模板。
Q / 01

自进化 harness

让系统从轨迹、失败与人工修正中学习“下一次如何更好”，但把可学习参数和不可突破的安全边界分开。

Q / 02

用什么语言？

底层需要强类型、可取消、可观测；上层需要声明式。未来更像“runtime + policy DSL”，而不是某一种万能语言。

Q / 03

抽象到哪一层？

稳定的不是 UI，也不是某家模型，而是 Conversation → Session → Turn → Item 这条可恢复的生命周期。

Q / 04

个性化 harness

同一底座可以拥有不同的记忆、审批阈值、工具集与表达风格；个性化应配置化，而非复制一套 runtime。
